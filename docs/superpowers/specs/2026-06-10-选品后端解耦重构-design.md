# 选品比价工具后端解耦重构 + 错误处理 + 流式 LLM 设计

> 日期:2026-06-10
> 范围:`backend/python/shopee-analyzer`(Python FastAPI 服务内部)
> 不在本期范围:relay 透传层、前端容错(断流重连)——前端仅做最小改动以支持逐字展示

## 1. 背景与现状

选品比价工具(前端路由 `/sourcing-tool`)的三层调用链路:

```
前端 src/lib/sourcing.ts
  → /api/shopee/sourcing/*  (relay:8765 server/src/routes/shopee.ts 透传代理)
    → 127.0.0.1:8000  (Python FastAPI shopee-analyzer ← 选品比价主体)
      ├─ aibuy_client.py     → 1688 h5api(搜图/拉商品)   [urllib,无重试]
      ├─ sku_provider.py     → 万邦 Onebound API(拉 SKU)  [urllib,sleep 1.5s 限流]
      ├─ sku_match_client.py → localhost:8001 langchain-agent(LLM 匹配) [跨服务一跳]
      └─ image_verify.py     → 中转 GPT vision(图文核对)  [urllib,无重试]
```

### 现状问题

1. **`sourcing.py` 786 行,职责混杂**:路由 / 业务编排 / SSE 生成 / 配置 CRUD 全混在一起。
2. **错误处理缺失**:4 个外部调用点几乎全无系统性重试,唯一"重试"是 aibuy token 过期硬重试一次;限流靠硬编码 `time.sleep(1.5s)`;`main.py` 多处 `raise HTTPException(500, traceback.format_exc())` 向客户端泄露堆栈。
3. **HTTP 底层全用 `urllib`**:无连接池、无流式、无超时细分;`httpx` 已装但未用。
4. **SKU 匹配跨服务一跳冗余**:LLM 调用绕到 langchain-agent(Node),但 Node 端 `sku-match.ts` 仅做 zod 校验 + 固定 prompt + `withStructuredOutput(jsonMode)`,没有任何只有 LangChain/Node 才有的能力(无状态单轮调用,未用到会话记忆/多轮/工具编排)。Python 侧 `image_verify.py` 早已直连中转 LLM,能力本就存在。
5. **GPT-5.5 调用全为非流式**:批量长耗时任务下,等完整 JSON 期间帧间静默易撞 nginx 60s 读超时(6ebb3f8 刚加心跳缓解);中转对非流式大 JSON 易 400/截断。

## 2. 目标与决策

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 改造重心 | Python 服务内部 | 收益最大,4 个外部调用点全在此 |
| SKU 匹配 LLM | **收回 Python 直连**,废弃 langchain-agent sku-match 路由 | Node 端无独有能力;消除一跳;流式少穿一层;prompt/schema 不再两地维护 |
| 流式范围 | SKU 匹配 + 图文核对两处 LLM 均改流式 | 三动机兼有:防超时保活 / 中转非流式稳定 / 前端逐字展示 |
| HTTP 底层 | **httpx + tenacity** | httpx 原生支持流式/超时细分/连接池;tenacity 提供指数退避 + jitter |
| 文件结构 | MVC 分层(FastAPI 习惯命名) | 工程化最佳实践,可独立测试 |

**核心解耦动作**

- `sourcing.py` 由 786 行瘦身为纯路由层;业务编排搬到 `services/sourcing_pipeline.py`。
- 新增 `clients/llm_client.py`:统一封装中转 LLM,SKU 匹配 + 图文核对共用;SKU 匹配的 prompt/schema 从 `langchain-agent/src/lib/sku-match.ts` 搬来。
- 删除 `sku_match_client.py`(调 Node 的客户端)。
- 保留 `sku_provider.py` 现有 provider 抽象,作为其他 client 的模板。
- 配置/凭证由模块级 `configure()` 全局可变状态,收敛为显式注入。
- `main.py` 拆出 `routers/shopee_store.py`,使店铺分析与选品比价两套业务解耦。

## 4. 错误处理策略

**核心原则:错误分类在 client 层判定,重试在 client 层执行,业务层只看到「成功 / 已分类的失败」。**

### 4.1 错误分类体系(models/errors.py)

```
SourcingError (基类)
├── RetryableError    # 可恢复 → tenacity 自动重试
│     触发:Timeout / ConnectionError / 429 / 500 / 502 / 503 / 504 / 流中断
├── PermanentError    # 不可恢复 → 立即失败,不重试,暴露原因
│     触发:400 参数错 / 401·403 鉴权风控 / 余额不足 / 业务规则不满足
└── UnknownError      # 未分类 → 记日志,保守失败(按不可恢复处理,不无限重试)
```

每个 client 把原始 HTTP 状态/异常翻译成这三类之一(类似 `should_raise_retryable`),上层无需懂各家错误格式。

### 4.2 重试退避策略(clients/http.py)

用 `tenacity` + `wait_random_exponential`(带 jitter,适合批量任务避免同时撞接口):

| 调用点 | stop | wait | 只重试 |
|--------|------|------|--------|
| 1688 搜图 (aibuy) | 3 次 | random_exp, max 30s | RetryableError |
| 万邦 SKU | 4 次 | random_exp, max 30s | RetryableError(429 慢退) |
| LLM(匹配/图文) | 3 次 | random_exp, max 20s | RetryableError + 流中断 |

判断准则:**指数退避只救「临时失败」,不救「方向错误」**。400/401/余额不足 → PermanentError,一次都不重试,原因冒泡到 SSE error 事件。

### 4.3 限流改造

现状硬编码 `time.sleep(1.5s)` 防万邦 503。改造:保留请求间最小间隔(主动节流防打爆),503 真发生时交给 tenacity 退避(被动救火)。两者职责分开。

### 4.4 不再泄露堆栈

`traceback.format_exc()` 只进结构化日志;返回前端的是分类后的人话错误 `{code, message}`。

## 5. 流式 LLM 改造

### 5.1 核心矛盾:流式 token vs 结构化 JSON

SKU 匹配需要结构化 JSON(`matched_sku_id`/`scores`/`overall_score`),但流式返回逐字 token,前端拿到半截 JSON 无法解析。解法:把「传输」和「解析」分开。

```
中转 API ──token流──> llm_client ──┬──> 累积成完整 JSON,解析成 SkuMatchResult(给业务用)
                                  └──> 同时把 raw token 转发出去(给前端逐字看)
```

### 5.2 llm_client.py 流式调用

httpx `stream=True` 调中转 `chat/completions`(`stream: true`),逐块读 SSE:

- 每个 delta token 累加进 buffer
- 通过回调 `on_token(token)` 往外吐(供上层透传前端)
- 流结束后对完整 buffer 做 `json.loads` + Pydantic 校验 → 返回结构化结果

业务层拿到的仍是干净的结构化结果,流式只是传输层的事。SKU 匹配 + 图文核对共用 `stream_structured()`。

### 5.3 保活:流式天然解决 nginx 60s 读超时

流式下每出几个 token 即有数据帧,帧间静默远小于 60s,nginx 读超时不触发。心跳从「应用层定时发空帧」退化为「自然有数据流」;原心跳逻辑保留作流真正卡住时的兜底。

### 5.4 SSE 透传到前端逐字展示

`sourcing_pipeline.py` 编排时把 `on_token` 回调接到 SSE 输出,新增事件类型:

```
event: llm_token
data: {"item_id": "xxx", "phase": "sku_match", "token": "评"}    ← 逐字
event: candidate_scored
data: {"item_id": "xxx", "match_overall_score": 87, ...}          ← 该候选最终结构化结果
```

前端 `sourcing.ts` 的 `analyzeStream` 已是逐帧解析 generator,只需新增对 `llm_token`(累积显示)和 `candidate_scored`(定格最终分)的处理。前端改动小。

### 5.5 流中断重试

- 流到一半断(连接重置)→ 按 RetryableError 整条重试(流式无断点续传)
- 重试时重新发起整个请求;前端已显示的半截 token 用 `llm_retry` 事件通知清空重来
- 若已积累 buffer 能 `json.loads` 成功(罕见),不重试,直接用
- 重试用完仍失败 → 降级 PermanentError,该候选标 `llm_failed`,**不阻塞其他候选**(批量任务,单候选挂不拖垮整批)

## 6. 测试策略(TDD 强制)

| 层 | 测什么 | 怎么测(不打真实外部 API) |
|----|--------|--------------------------|
| `services/cost_calculator` | 成本/利润/推荐等级纯计算 | 纯函数断言(迁移现有 test_calc_cost_matched_sku 等) |
| `services/sourcing_pipeline` | 编排顺序、单候选失败不阻塞批次、事件产出 | 注入 fake clients(stub),断言事件序列 |
| `clients/llm_client` | 流式累积成 JSON、解析失败、流中断重试 | `httpx.MockTransport` 喂构造的 SSE 流 |
| `clients/http` 重试策略 | 429/503 触发重试、400 不重试、退避次数 | MockTransport + 计数断言;tenacity wait 设 0 免空等 |
| `clients/aibuy` / `sku_provider` | 错误分类翻译正确 | MockTransport 喂各状态码,断言抛对应错误类 |
| `routers/sourcing` | 入参校验、SSE 帧格式 | FastAPI TestClient,service 用 stub |

关键:用 `httpx.MockTransport` 替代真实网络,重试/流式/错误分类均可在单测确定性复现。每个新 client/service 先写失败测试(RED)→ 最小实现(GREEN)→ 重构。

## 7. 迁移顺序(自底向上,每步可独立验证,不破坏线上)

```
Step 1  core/ + clients/http.py + models/errors.py        基础设施,先立住
Step 2  clients/llm_client.py(流式 + 结构化)              搬 sku-match.ts prompt/schema
Step 3  各 client 接入 http.py + 错误分类                  逐个替换 urllib→httpx,跑回归
Step 4  services/ 抽编排 + cost_calculator                业务逻辑搬出 sourcing.py
Step 5  routers/ 瘦身 + main.py 拆 shopee_store           SSE 新增 llm_token 事件
Step 6  前端 sourcing.ts 加 llm_token 处理                逐字展示
Step 7  删 langchain-agent/sku-match + sku_match_client.py 新链路验证稳定后才删,留回滚
```

**安全网**:Step 7 删旧链路放最后。前 6 步完成并验证稳定前,langchain-agent 的 sku-match 保持可用,随时回滚(符合「生产操作:备份→验证→单点改动」守则)。

**部署校验**:每步 `git add` 关联文件,Python 端 `pytest` 全绿 + 新文件全部提交,避免「本地能跑、服务器构建失败」。
