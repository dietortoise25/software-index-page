# AI 需求助手 — 整合 grill-with-docs 审查引擎

> 当前状态：AI需求助手 = 4阶段需求收集 → 输出结构化JSON  
> 目标状态：AI需求助手 = 需求收集 + grill-with-docs审查 → 输出审查后的需求文档

---

## 当前流程 vs 目标流程

```
当前：用户描述 → 4阶段收集 → JSON → 提交审查面板

目标：用户描述 → 4阶段收集 → 术语对齐 → 设计审查 → 审查后需求文档 → 提交
                         └─ grill-with-docs ─┘
```

---

## 新增两个阶段

### 阶段 5 — 术语对齐

AI 检查需求中的关键术语是否与项目已有术语冲突。

**输入**：阶段 1-4 收集到的用户陈述  
**参考**：项目 `CONTEXT.md` 术语表、已有 `docs/adr/` 决策

**工作步骤**：

| 步骤 | 动作 | 示例 |
|------|------|------|
| 5.1 | 提取需求中所有关键名词/动词 | "订单取消"、"用户账号"、"退款" |
| 5.2 | 逐个对比 CONTEXT.md 术语表 | "账号" — 是 Customer 还是 User？项目中已区分这两个概念 |
| 5.3 | 模糊术语精准化，向用户确认 | "你说的'取消订单'是指整单取消还是部分取消？项目中 CONTEXT.md 定义了 partial_cancel 和 full_cancel" |
| 5.4 | 术语达成一致后，更新 CONTEXT.md（新增术语或澄清已有） | 直接在对话中输出术语变更建议 |
| 5.5 | 将澄清后的术语替换到需求描述中 | — |

**对话示例**：

```
AI: 你提到"订单取消"，项目 CONTEXT.md 中定义了两种取消：
    - partial_cancel：取消订单中部分商品
    - full_cancel：取消整个订单
    你说的需求是哪种？还是两者都涉及？

用户: 整单取消

AI: 已记录。需求中将使用 full_cancel 表示整单取消。
```

### 阶段 6 — 设计审查

逐项追问设计树上的每个分支，直到达成共识。

**工作步骤**：

| 步骤 | 动作 | 示例 |
|------|------|------|
| 6.1 | 梳理需求的设计树（分支节点） | 数据存储选型 → 文件 vs 数据库 vs Supabase |
| 6.2 | 对每个分支节点追问 | "你提到要存储需求数据，已有 server JSON 存储，新增数据是否沿用？还是需要新建表？" |
| 6.3 | 用具体场景边界测试 | "如果同时有两个审批人操作，会发生什么？" |
| 6.4 | 代码交叉验证 | "你提到审批流走飞书，现有代码 server/src/routes/approval.ts 已经是原生审批了，需求中指的是这个还是新增渠道？" |
| 6.5 | 识别需要 ADR 的决策（不可逆/反直觉/有真实权衡） | "从三方审批切换到原生审批这个决定建议记录为 ADR" |
| 6.6 | 逐节点关闭，直到设计树无剩余分支 | — |

**对话示例**：

```
AI: 你的需求涉及"负责人变动审批"。设计树上有几个分支需要确认：

    分支 1：审批流在哪里？
    - A. 飞书原生审批（已有 server/src/routes/approval.ts）
    - B. 三方审批（旧系统，已弃用）
    
    你用的是 A 对吧？但当前代码只传了固定审批人 Alan，你需要支持动态审批人吗？

用户: 对，要动态指定

AI: 好，分支 1 关闭。分支 2：变动记录存储
    当前 shop_operator_changes 表在 Supabase internal schema，新需求是复用还是独立表？
    ...
```

|------|------|------|------|

## 前端实现方案

### ChatDialog 状态机扩展

```
当前：chat → preview → scheduling → submitting → done

目标：chat → term_alignment → design_review → preview → scheduling → submitting → done
```

新增两个阶段：
- `term_alignment`：AI 进入术语对齐模式
- `design_review`：AI 进入设计审查模式

### 后端 Prompt 改造

`interview-prompt.ts` 需要拆分为三套 Prompt：

| Prompt | 用途 | 触发时机 |
|--------|------|---------|
| `COLLECTION_PROMPT` | 阶段 1-4 需求收集（复用当前） | 对话开始 |
| `TERM_ALIGNMENT_PROMPT` | 阶段 5 术语对齐 | 收集完成后自动触发 |
| `DESIGN_REVIEW_PROMPT` | 阶段 6 设计审查 | 术语对齐后自动触发 |

每套 Prompt 注入对应的 grill-with-docs 行为规范。

---

## 启动方式

在 ChatDialog 顶部增加模式选择：

| 模式 | 说明 |
|------|------|
| **快速提交** | 跳过审查，直接走 4 阶段收集 → 输出 JSON（当前行为） |
| **需求审查**（默认） | 完整 6 阶段：收集 → 术语对齐 → 设计审查 → 输出 |

用户可在对话开始时切换，或在第 4 阶段完成后由 AI 询问是否进入审查。
